# Epistel architecture

Design for the first release (0.1). Items marked "later" are listed in
[roadmap.md](roadmap.md) with the reason they are deferred.

## 1. Problem

A domain whose mail is handled by Amazon SES can receive and send messages,
but has no mailboxes. SES drops received mail into a bucket or hands it to a
function; it offers nothing a mail client can connect to. The usual
workaround is forwarding to a mailbox somewhere else, which moves the mail
out of the account and breaks sender alignment on the way.

Epistel keeps the mail inside the operator's own account and serves it to
standard mail clients.

## 2. Scope

In scope:

- Serve mailboxes over IMAP.
- Accept outgoing mail over SMTP Submission and relay it through the mail
  service.
- Ingest received mail from the mail service.
- Accounts, app passwords, addresses, aliases and catch-all addresses,
  managed from a command line.

Out of scope, permanently:

- Acting as a mail transfer agent: no port 25, no MX handling, no outbound
  queue with retries to remote hosts, no DKIM signing, no spam or virus
  engine. The mail service does all of this.
- POP3, STARTTLS, plaintext listeners, legacy authentication mechanisms
  (LOGIN, CRAM-MD5, NTLM).

Out of scope for 0.1, planned later: see the roadmap.

There are no compatibility promises before 1.0. Storage schema,
configuration format and command line may change between releases without
migration paths.

## 3. Protocol profile

One profile, not a matrix of options.

| Purpose | Protocol | Port | Transport |
|---|---|---|---|
| Read mail | IMAP4rev1 with the extensions below | 993 | implicit TLS |
| Send mail | SMTP Submission (RFC 6409) | 465 | implicit TLS (RFC 8314) |

TLS:

- TLS 1.3. TLS 1.2 is accepted only with ECDHE and AEAD cipher suites.
  Nothing older.
- The server terminates TLS itself. Certificate and key are read from files
  and reloaded when they change, so any issuing method that produces files
  works.

Authentication:

- SASL PLAIN, on both protocols, only inside TLS.
- The secret is an app password: generated by the server, high entropy,
  shown once, one per device, individually revocable. Stored as an Argon2id
  hash. Users never choose a password.
- IMAP's own `LOGIN` command is accepted next to `AUTHENTICATE PLAIN`. It
  carries the same user name and app password under the same TLS, and
  several mainstream clients use nothing else. The legacy SASL mechanisms
  stay out.
- A failed login is answered after a fixed delay, and an unknown user costs
  the server as much time as a wrong password.
- OAuth (OAUTHBEARER) is later. Mainstream clients only offer OAuth for a
  fixed list of large providers, so it would add little today.

IMAP capabilities in 0.1: `IMAP4rev1`, `AUTH=PLAIN`, `SASL-IR`, `LITERAL+`,
`ID`, `ENABLE`, `NAMESPACE`, `UNSELECT`, `SPECIAL-USE`, `IDLE`, `UIDPLUS`,
`MOVE`. IMAP4rev2 is on the roadmap: every client in use speaks IMAP4rev1,
and announcing the newer revision obliges the server to more than its
extensions already give.

SMTP extensions in 0.1: `AUTH PLAIN`, `SIZE`, `8BITMIME`, `PIPELINING`,
`ENHANCEDSTATUSCODES`, `SMTPUTF8`.

## 4. Components

```
                    internet
                       |
                  mail service  (MX, DKIM, scanning, delivery)
                  /          \
        received mail        outgoing mail
     (object + event)        (send API)
                |                ^
                v                |
        +-------+----------------+--------+
        |            Epistel              |
        |                                 |
        |  ingest      IMAP    submission |
        |     \         |         /       |
        |      +--- mail core ---+        |
        |        |             |          |
        +--------+-------------+----------+
                 |             |
          metadata store   blob store
                 
        mail clients --993/465 TLS--> Epistel
```

- **Ingest** pulls received-message events from the mail service, stores the
  message, and files it into the right mailboxes.
- **IMAP** serves mailboxes to clients.
- **Submission** accepts outgoing messages from authenticated clients and
  relays them.
- **Mail core** holds the domain logic: accounts, address resolution,
  mailbox and message operations, change notification.
- **Admin** is a set of subcommands in the same binary.

One process runs all of them. The process keeps no state on disk.

## 5. Vendor independence

Every external dependency sits behind an async trait defined in the core
crate. The core, IMAP and Submission crates do not name any vendor. The
binary reads the configuration and wires in one implementation per trait.
Changing vendor is a configuration change once a second implementation
exists.

| Trait | Responsibility | 0.1 implementation |
|---|---|---|
| `MetadataStore` | accounts, credentials, addresses, mailboxes, message records, counters | DynamoDB |
| `BlobStore` | immutable message bodies | S3 |
| `InboundSource` | stream of received messages with envelope and verdicts | SES receipt events over SQS |
| `OutboundRelay` | send one raw message to a list of envelope recipients | SES v2 send API |
| `ChangeBus` | tell open sessions that a mailbox changed | in-process |

Rules that keep the traits honest:

- **Operations are stated in mail terms, not storage terms.** The trait says
  "append this message to this mailbox and return its UID", not "put item"
  or "run query". A key-value store, a document store and a SQL database
  can each implement it in their natural way.
- **Atomicity requirements are part of the contract.** Each method documents
  what must be atomic (for example: UID allocation and message record
  creation happen together or not at all; a UID is never reused).
- **In-memory implementations exist from the first commit.** They back the
  protocol tests and prove the traits are implementable twice.
- **One conformance test suite per trait.** Every implementation must pass
  the same suite. A new backend is done when the suite is green.
- **No vendor types cross the trait.** Errors, identifiers and pagination
  tokens are core types.
- **Vendor crates are optional features**, so a build can leave out what it
  does not use.

Crate layout:

| Crate | Contents |
|---|---|
| `epistel-core` | domain types, traits, mail core logic, in-memory implementations, conformance suites |
| `epistel-imap` | IMAP protocol server |
| `epistel-submission` | SMTP Submission protocol server |
| `epistel-aws` | DynamoDB, S3, SQS and SES implementations |
| `epistel` | binary: configuration, wiring, listeners, admin commands |

## 6. Data model

| Entity | Key facts |
|---|---|
| Account | id, display name, state (active, suspended) |
| Credential | belongs to an account; label, Argon2id hash, created, last used |
| Address | full address or `*@domain`; points at an account |
| Mailbox | belongs to an account; name, special-use role, subscribed flag, `UIDVALIDITY`, next UID, highest modification sequence |
| Message record | belongs to a mailbox; UID, blob reference, size, internal date, flags, modification sequence, cached envelope and body structure |
| Blob | the raw message, immutable; reference count kept in the metadata store |

Notes:

- The login name is the account's primary address.
- Every account starts with `INBOX`, `Drafts`, `Sent`, `Junk`, `Trash` and
  `Archive`, with special-use attributes set.
- A message delivered to several mailboxes, or copied, shares one blob.
  The blob is deleted when its count reaches zero. A periodic sweep removes
  blobs orphaned by a crash between the two steps.
- Envelope, body structure and header fields are computed from the stored
  message when a client asks for them, so those requests read the blob.
  Keeping the header block on the message record, so that listing a mailbox
  never touches the blob store, is planned before 0.1 (see the roadmap).
- The modification sequence is recorded from day one even though
  `CONDSTORE` is later; adding the extension then needs no data change.

DynamoDB mapping (one table, partition key `pk`, sort key `sk`):

| `pk` | `sk` | Item |
|---|---|---|
| `ACCOUNT#<account>` | `META` | account, and its counter for `UIDVALIDITY` values |
| `ACCOUNT#<account>` | `CRED#<credential>` | credential |
| `ACCOUNT#<account>` | `ADDR#<pattern>` | marks a pattern the account owns, for listing |
| `ACCOUNT#<account>` | `MBOXNAME#<name>` | reserves a mailbox name, points at the mailbox |
| `ACCOUNTS` | `<primary address>` | directory of accounts, for listing |
| `ADDR#<pattern>` | `META` | owner of a pattern |
| `MBOX#<mailbox>` | `META` | mailbox with its counters |
| `MBOX#<mailbox>` | `MSG#<UID, ten digits>` | message record |
| `BLOB#<blob>` | `META` | reference count; a marker once released |
| `INGEST#<key>` | `META` | a filed delivery, written with its message record |

`expires_at`, in seconds since the epoch, is the table's time-to-live attribute.
All reads are strongly consistent.

Uniqueness (one owner per address, one mailbox per name) comes from conditional
writes inside transactions. An append takes its UID with an atomic counter
update on the mailbox item and then stores the record; a failure in between
leaves a UID unused, which IMAP allows. Removing a record and releasing its blob
are two steps, as are deleting a mailbox and removing its contents; a failure in
between leaves unreferenced items for the sweep, never a dangling reference.
This mapping is private to `epistel-aws`.

## 7. Inbound flow

1. The mail service accepts a message for the domain, scans it, writes the
   raw message to an object store and emits an event carrying the envelope
   recipients and the spam, virus, SPF, DKIM and DMARC verdicts.
2. `InboundSource` yields the event together with a handle for reading the
   raw bytes.
3. Each envelope recipient is resolved to an account: exact address, then
   catch-all for the domain. Unresolved recipients are logged and dropped.
   Epistel does not generate bounces for unknown recipients; doing so after
   acceptance produces backscatter. Two addresses of one account are one
   delivery.
4. If any account is left, ingest reads the message and writes it to
   `BlobStore` once; all recipients share the blob.
5. The message is filed per account: the quarantine mailbox, invisible to
   the client, if the virus verdict failed; `Junk` if the spam verdict
   failed; otherwise `INBOX`. A special mailbox the user deleted falls back
   to `INBOX`, and a missing `INBOX` brings the default mailboxes back.
6. `ChangeBus` tells sessions that have the mailbox open.
7. Ingest acknowledges the event. The source forgets it and removes the
   original object.

Losing no mail and doubling none:

- The source offers a message at least once, and acknowledgement comes only
  after every recipient is dealt with. A failure anywhere leaves the message
  with the source.
- Filing is exactly once. Each append carries a key made of the message and
  the account, and the metadata store records the key together with the
  message record, in one atomic step, refusing a key it has seen. A message
  offered again is recognized per account.
- A message that keeps failing, or a queue entry that is not a usable event,
  is never acknowledged. The queue's redrive policy moves it to the
  dead-letter queue, and the raw message stays in the object store for
  inspection.

With SES, the envelope recipients exist only in the receipt event, never in
the message itself, which is why ingest is driven by the event and not by
the object store. The source reads the queue fed by the receipt rule's
topic, with or without raw message delivery.

Ingest does not parse the message. What IMAP needs from the headers and the
MIME structure is extracted when the IMAP read path is built.

## 8. Outbound flow

1. A client connects on 465 and authenticates.
2. `MAIL FROM` and the `From` header must both be an address the account
   owns. Otherwise the message is rejected with `550 5.7.1`.
3. The declared and actual size must not exceed the relay's limit (40 MB
   for SES).
4. The `Bcc` header is removed. `Date` and `Message-ID` are added if
   missing.
5. `OutboundRelay` sends the raw message to the envelope recipients, split
   into batches when the relay limits recipients per call (50 for SES).
6. The relay's answer maps onto the SMTP reply: accepted is `250`,
   throttling or a transient fault is `451`, a permanent refusal is `550`.

There is no outbound queue. The relay call happens inside the SMTP
transaction; on a transient failure the client keeps the message and tries
again, which every client already does.

The copy in `Sent` is the client's job, done with IMAP `APPEND`, as with any
other IMAP server.

Bounces need no special handling in 0.1: the mail service returns them as
ordinary mail to the sender address, and they arrive through the inbound
flow.

## 9. IMAP server

- One task per connection. Session state is the authenticated account, the
  selected mailbox, and for each of its messages the UID and the modification
  sequence the client was last told the flags of.
- Commands are parsed with `imap-codec`, including synchronizing and
  non-synchronizing literals. Responses are written by the server's own
  writer. MIME structure and address lists are parsed by the server's own
  code, because IMAP reports byte ranges and header text exactly as received.
- Commands: `CAPABILITY`, `NOOP`, `CHECK`, `LOGOUT`, `ID`, `LOGIN`,
  `AUTHENTICATE PLAIN`, `ENABLE`, `NAMESPACE`, `LIST`, `LSUB`, `STATUS`,
  `SELECT`, `EXAMINE`, `UNSELECT`, `CLOSE`, `CREATE`, `DELETE`, `RENAME`,
  `SUBSCRIBE`, `UNSUBSCRIBE`, `APPEND`, `FETCH`, `STORE`, `COPY`, `MOVE`,
  `SEARCH`, `EXPUNGE`, `IDLE`, and the `UID` forms.
- Announced capabilities are exactly what is implemented.
- `SELECT` opens for reading and writing, `EXAMINE` for reading only. Reading
  a message body in a mailbox open for writing marks it as read; `BODY.PEEK`
  does not.
- A copy points at the same stored message as its original; nothing is
  duplicated. `MOVE` is a copy followed by the removal of the original.
- Keeping the client current: on `NOOP`, `CHECK`, `EXPUNGE`, `MOVE`, an
  `APPEND` to the open mailbox, and while idling, the server compares the
  mailbox with what the client was told and reports removals, arrivals and
  changed flags. Sequence numbers never shift inside `FETCH`, `STORE` or
  `SEARCH`.
- `IDLE`: every change to a mailbox is published on `ChangeBus`; an idling
  session hears of it at once and looks. A keepalive line goes out every two
  minutes so that nothing between client and server drops a quiet connection.
- `SEARCH` on flags, dates and size is answered from message records. Header
  and text searches read blobs and compare the text as stored, without
  decoding; clients keep their own index.
- Mailbox management: creating a mailbox creates the levels above it;
  renaming moves what is inside along; a mailbox with mailboxes inside is not
  deleted. The inbox cannot be deleted or renamed. The quarantine mailbox is
  never listed and cannot be opened.
- Mailbox names are stored as the client sends them. A client that encodes
  non-ASCII names in modified UTF-7 gets them back the same way.
- A connection that stays silent is closed: after one minute before login,
  after 31 minutes after it. A command longer than 64 KiB ends the connection;
  an appended message may be as large as the configured message size.

## 10. Security

- Only TLS listeners exist. There is no way to configure a plaintext one.
- App passwords only; hashes are Argon2id with parameters in configuration.
- Failed authentication is rate limited per source address and per account,
  with exponential delay. Limits are in memory in 0.1.
- Connection limits per source address and per account.
- No credentials in the configuration file. Cloud access uses the identity
  of the host (instance role on AWS).
- Message content and credentials are never logged. Logs carry connection,
  account and message identifiers only.
- Encryption at rest is the storage backend's duty and is required by the
  reference infrastructure.
- Parsers are fuzzed. The process needs no privileges beyond binding its
  ports and runs as an unprivileged user.

## 11. Configuration

One TOML file. Sketch:

```toml
[server]
hostname = "mail.example.org"

[tls]
certificate = "/etc/epistel/tls/fullchain.pem"
private_key = "/etc/epistel/tls/key.pem"

[imap]
listen = "[::]:993"

[submission]
listen = "[::]:465"
max_message_size = "40MB"

[metadata]
backend = "dynamodb"
table = "epistel"

[blobs]
backend = "s3"
bucket = "example-epistel-mail"
prefix = "blobs/"

[inbound]
backend = "ses-sqs"
queue_url = "https://sqs.eu-west-1.amazonaws.com/123456789012/epistel-inbound"

[outbound]
backend = "ses"
```

Each `backend` value selects an implementation of the corresponding trait;
the remaining keys in the section belong to that implementation.

## 12. Administration

Subcommands of the `epistel` binary, acting on the metadata store directly:

- `epistel account add | list | suspend | resume | remove`
- `epistel password new | list | revoke`
- `epistel address add | list | remove` (including `*@domain`)
- `epistel check`
- `epistel serve`

They need the same configuration file and the same cloud identity as the
server, so they are run on the server host or from an operator machine with
equivalent access.

## 13. Operations

- One instance. A second instance would work for storage, but sessions on
  different instances would not see each other's changes until the client
  polls; a shared `ChangeBus` is later.
- The instance is disposable. Replacing it loses nothing.
- Graceful shutdown sends `BYE` to IMAP sessions and finishes Submission
  transactions in flight.
- Structured logs on standard output. Metrics are later.

## 14. Testing

- Unit tests for mail core against in-memory implementations.
- Conformance suites for each trait, run against the in-memory and the AWS
  implementations.
- Protocol tests that drive the IMAP and Submission servers with independent
  client libraries.
- Fuzzing of the IMAP and SMTP parsers.
- A manual client matrix before each release: Outlook (classic and new),
  Thunderbird, Apple Mail, iOS Mail, one Android client.

## 15. Building blocks

- `tokio` for the runtime, `rustls` for TLS.
- `imap-codec` for IMAP parsing and serialization.
- `mail-parser` for MIME.
- The official AWS SDK for Rust inside `epistel-aws`.
- `argon2` for password hashing, `tracing` for logs.

The SMTP Submission server is small enough to write directly.
